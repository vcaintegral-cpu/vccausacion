- Password recovery uses a separate email-only form with persistent request feedback and session validation on the public reset page, so login-required fields and transient notifications cannot hide recovery failures.

- RECIBIDOS purchases use a pure workbook parser and an adapter into the shared PDF draft-accounting function, with one persisted task per document, so extraction remains AI-free without duplicating accounting logic.
- Purchase confirmation recomputes rules with user-scoped reads, then calls an atomic service-only SQL transaction after membership checks, to prevent client journal tampering and partial writes.
- PDF and RECIBIDOS purchases use the same Siigo posting function and payload mapping, with shared expense/source/duplicate/readback gates; Contai exports continue to use stored journal rows to avoid divergent accounting.
- The shared account engine validates expense groups at every assignment boundary and journal construction; approval is additionally guarded in PostgreSQL to prevent bypasses.
- Bulk imports preload company purchase knowledge under user-scoped RLS, retain per-line provenance in raw extraction metadata, and persist bounded groups before marking items complete to avoid per-line network calls.
- Rejected dynamic-module imports require an explicit document reload in the root error boundary; router invalidation cannot clear the browser's rejected module cache.
- Source snapshots store integer cents, database monetary columns store currency units, and all comparisons convert at the boundary; source-backed approval and exports validate the stored journal without changing invoice amounts.
- Account selectors share a catalog-identity hierarchy index and filter the full catalog before bounding rendered results, avoiding repeated full accounting evaluations and oversized menus on the main thread.
- Source-declared IVA rates resolve only an unambiguous active tax record and persist its exact ID without recalculating amounts; bounded, labeled document adjustments are classified separately from purchase expenses.
- Siigo preflight forecasts taxes from serialized item precision and the live company tax catalog; readback reconstructs gross purchase totals from Siigo net totals plus actual retentions, without altering source values or resending existing identities.
- Siigo error recovery state (error kind, attempts, request/response trace, voided consecutives) is persisted on the invoice and remote-identity rows are never resent or deleted (DB trigger), so recovery actions survive sessions and cannot duplicate Siigo documents.
- Support documents (DS) reuse the invoices table with doc_kind='soporte' and the shared saveExtractedInvoice engine; purchase views filter doc_kind='compra'. Sending uses POST /v1/purchase-support-documents in siigo-support.functions.ts; recovery picks the Siigo path by doc_kind.
- DS numbering: the cuenta de cobro number is the DSEB consecutive Siigo assigns at creation (never computed in-app); batches send one-by-one ordered by operation date then vendor name; duplicates are detected by vendor+date+total and need user confirmation; after creation a numbered "Cuenta de cobro" PDF (src/lib/cc-pdf.server.ts, pdf-lib) is stored in the facturas bucket at <user_id>/<company_id>/soporte-cc/<invoice_id>.pdf and saved to invoices.cc_pdf_path.
- Support documents are created in Siigo with stamp.send=false and mail.send=false and the app never calls any DIAN send/stamp endpoint; readback stamp status flags unauthorized transmission (invoices.ds_unauthorized_transmission) and stops the batch, because the user transmits to DIAN from Siigo. Batch creation stays limited to one document until company_parameters.ds_batch_enabled is confirmed.
- After creating a DS, src/lib/ds-finalize.server.ts reads Siigo's consecutive (response → GET by id → date/vendor/total search), stores it as prefix-number using the active DIAN resolution prefix (fallback: Siigo document name), regenerates the cuenta de cobro PDF and PUTs observations only while the document is not yet sent to DIAN, never retrying; the same helper backs "Traer consecutivo de Siigo".
- Document sources (Fuentes de documentos): per company one COMPRAS and one EGRESOS folder on Google Drive or OneDrive/SharePoint, behind a shared read-only FileProvider. Imports run server-side only: purchase PDFs and RECIBIDOS documents go into the existing bulk queue (bulk_uploads/items "pending", storage <owner>/<company>/fuentes|excel/...) so the browser bulk-runner keeps doing extraction/causación with one engine; egresos files go to payment_documents. Dedup by external ID (document_source_files) and SHA-256 / excel:<key> fingerprints; RECIBIDOS is re-read when modified. OAuth refresh tokens live in document_connections (service-only; Microsoft rotates them). Runs from pg_cron → /api/cron/document-sync (x-cron-secret); listing is batched because the Worker caps subrequests.

- Tax precedent per provider (src/lib/precedente-tributario.ts, global): learned from documents with Siigo identity (invoice_lines.iva_tax_id, header retentions + 2365/2367/2368 journal accounts) and Siigo auxiliar history (accounting_history 2408/236x). Drafts pick the exact IVA tax among same-rate taxes by provider precedent (no rate inference: without a source rate, only a precedent tax whose rate matches the line to the peso) and fill the IVA journal account; retentions not reported by the document are applied from precedent only if the base reaches the concept's base mínima (retention_base_tables: dated tables, per concept the latest valid_from covering the invoice date; UVT × base rounded to the nearest 1,000 per art. 868 E.T.; × tax_rates.retention_concept, fallback tax_rates.min_base; seeded with the firm's 2026 table from src/lib/bases-minimas-2026.ts); provider rules and document-reported retentions still win. Providers without retefuente precedent require confirming their condition, stored in providers.purchase_tax_profile.condicion_retencion. Precedent and bases are cached 5 minutes and shared by the batch.

- Egresos y recibos de pago (RP): module /egresos (núcleo). CxP are read from Siigo GET /v1/accounts-payable into siigo_cuentas_por_pagar (provider invoice mapped from invoices.siigo_number or Siigo purchases' provider_invoice). Each payment of the month is an `egresos` row with a pure proposal (src/lib/egresos.ts): DebtPayment to one or several FC dues, abono, AdvancePayment, or Detailed (debit concept account / credit bank) using rules taught on screen (egreso_reglas) and CE/RP precedent from accounting_history. Sent one by one after approval with a lock; rows with siigo_id are immutable (trigger). The monthly «Consolidado» payments report is company-specific (function lector_consolidado_pagos) and read from the EGRESOS Drive source (Google Sheets exported to xlsx) or uploaded.
- Conciliación bancaria: module /conciliacion (núcleo). Per account (egreso_reglas banco: label → bank/cash account) and month it crosses the statement (Bancolombia Excel from the EGRESOS inbox; with lector_consolidado_pagos also the monthly report's bank and «Efectivo» sheets, stored as payment_documents kind relacion_pagos, whose «Consolidado» cites RC/RP), Siigo books (uploaded auxiliar, completed with API RCs and RPs sent by the tool) and the previous cut-off items (conciliaciones_bancarias). Pure engine src/lib/conciliacion.ts: voucher refs → monthly bank-fee group → exact amount ±0..31 days with name tiebreak → N:1 (payroll). Result: missing RPs, income without RC, value differences, items at cut-off; exported to Excel in the format re-read next month.
- Conciliación extras: bank PDF statements (Davivienda) are parsed in the browser (pdfjs → src/lib/extracto-pdf.ts) and, when the monthly report has that bank's sheet, compared with it (unreported movements) while the PDF becomes the statement carrying the sheet's RC/RP refs. Rounding differences within the egresos tope are sent from the module as a Siigo journal (conciliacion_ajustes, one per difference key, immutable once in Siigo). Siigo movement can be rebuilt from the API (journals, vouchers, payment-receipts, invoices, purchases by payment type) for a date range and validated against POST /v1/test-balance-report (src/lib/siigo-movimiento.server.ts); the uploaded auxiliar remains the fallback. Payment gateways (function pasarelas_pago, src/lib/pasarelas.ts): platform sheets (Bold, Wompi) give gross/commission/IVA/retentions/net per charge; charges are crossed with RC (gross) and bank deposits (net, by cited RC or same net 0–5 days); the month's deductions of deposited charges become one RP per platform and account in Egresos (origen pasarela, DebtPayment of the commission invoice + retention lines, credit bank), and the engine reconciles net deposits vs gross RC with that RP.
- RC/RP booked to the wrong bank: detectarCuentaErrada pairs an RC/RP left in one account's books (not in its statement) with an unrecorded movement of another account's statement (cited voucher, then same amount ±5 days); selected items are fixed with one Siigo reclassification journal each (conciliacion_ajustes tipo reclasificacion, wrong → right account, same third party; the original receipt is never edited — the Siigo API cannot edit RC/RP). Once sent, the journal cancels the receipt in the wrong account and crosses the deposit in the right one.
- Per-line actions in /conciliacion: an unrecorded statement outflow becomes a Detailed RP in Egresos (origen conciliacion, debit chosen account / credit bank, chosen third party; optionally approved and sent via egresosEnviar); an unrecorded inflow becomes a Detailed RC in Siigo (/v1/vouchers, conciliacion_ajustes tipo registro_rc); a value difference becomes a journal against a chosen account (tipo ajuste, no tope). Any line can instead stay as a partida conciliatoria with a note (PartidaConciliatoria.nota, keyed by clavePartida, saved with the month and exported). Journals and RC with manual numbering get the next consecutive (siigoCrearComprobante).
- /conciliacion keeps its working state per company in an in-memory store (usePersistente) so switching panels does not lose it, and silently refreshes sources on return. Lists support selecting rows (or all) for batch actions: leave as partida with one note, or register them in ONE Siigo document with the same account and third party (conciliacion_ajustes tipo lote with detalle lines: RP Detailed for outflows, RC Detailed for inflows, one journal for differences; dated month end); the engine crosses a batch document against each grouped statement movement.
- Statement outflows without RP are matched against live AP (siigo_cuentas_por_pagar, src/lib/cxp-sugerencias.ts: cited invoice number, NIT or similar name, one invoice or 2–4 summing the amount ±1) and can be paid in Siigo as a DebtPayment RP (conciliacionRegistrarRpFacturas → egresos origen conciliacion → egresosEnviar); AP can be re-synced from the screen. Company function reporte_conciliacion_firma (LED) downloads one workbook per account in the firm's format (src/lib/conciliacion-reporte.ts: «Reporte Conciliación» + working sheet «CONCILIACION <MES>» with columns D/E and formulas), which the previous-cut reader re-reads.
- Engine checks per account (verificarArrastre): statement opening balance vs previous cut's statement balance, books opening vs previous cut's books (+ back-dated items when the opening comes from the current trial balance), and opening difference vs previous partidas; tercerosDudosos flags crossed receipts whose third party shares no word with the bank/relación name. Partida notes travel with the partida to the next cut (MovBanco/MovLibro.nota). Chosen account and third party for a statement line are learned per description pattern (egreso_reglas concepto `conc:<tipo>:<patrón>`) and prefilled next time; downloading the firm format saves the month first.
- Piloto automático (function piloto_automatico + module piloto, LED): pg_cron every 10 min overnight (docs/piloto-automatico-cron.sql) → POST /api/cron/piloto (x-cron-secret) → avanzarPiloto (src/lib/piloto.server.ts) does ONE step per active company inside its night window (piloto_config.hora_inicio … 7 a. m. Colombia), persisting the night in piloto_ejecuciones (memoria) with steps drive → borradores → siigo_compras → egresos → gastos_bancarios → conciliacion → reporte (errored steps retried 3×). Questions it cannot decide go to piloto_decisiones and are emailed (Resend, RESEND_API_KEY / PILOTO_CORREO_REMITENTE) with one-tap signed links (/api/piloto/decision?t=token&o=opción) or answered in /piloto; the report is emailed once at the end. Stage 1a only runs Drive and reports the queue; server-side causación, Siigo sending, egresos and conciliation steps come next. Night window starts at 18:00; the cron runs all day so retries can resume right after publishing. Error loop: a step failing 3× opens an issue «piloto-error» in the PRIVATE repo vcaintegral-cpu/vccausacion-alertas (src/lib/alertas.server.ts, GITHUB_ALERTAS_TOKEN/GITHUB_ALERTAS_REPO; client data never goes to the public repo); a scheduled Claude routine fixes it, merges the fix, labels the issue «listo-para-publicar»; the pilot then emails a «Ya publiqué en Lovable» decision and, when confirmed, reopens the last night without its errored steps and retries them (even by day), re-sending the report.

## REGLA PERMANENTE: alcance de cada cambio (empresas)

Mapa completo: `docs/ARQUITECTURA.md`. Perfiles: `src/empresas/README.md`.

1. **Antes de modificar código por una instrucción, preguntar siempre a la usuaria
   su alcance**: ¿aplica a **todas las empresas** registradas y futuras, o solo a
   **empresas específicas** (cuáles, por nombre/NIT)? No asumirlo, aunque parezca obvio.
   Se exceptúan solo las correcciones de errores que dejan el resultado igual para
   todas (aun así, informar que el cambio es global).
2. **Todas las empresas** → cambiar el núcleo (`src/lib`, `src/routes`,
   `src/components`, `src/empresas/global.ts`).
3. **Empresas específicas** → declarar una función en `src/empresas/global.ts`
   (`FUNCIONES`), encenderla/apagarla en `src/empresas/<empresa>/perfil.ts` y
   condicionar el comportamiento con `funcionActiva()` / `usePerfilActivo()`. El
   comportamiento de las demás empresas no cambia. Empresa sin perfil → crearlo
   desde `src/empresas/_plantilla/` y registrarlo en `src/empresas/registro.ts`.
4. Nunca escribir NIT, nombres de empresa ni condiciones `if (empresa === …)`
   dentro del núcleo: todo lo particular va en el perfil.
5. Los datos contables de cada empresa (PUC, terceros, reglas por proveedor, IVA,
   retenciones, Siigo) siguen en la base de datos aislados por `company_id`.
6. Indicar el alcance elegido en el commit y en la solicitud de cambio
   ("Alcance: todas las empresas" / "Alcance: LED LIGHTS (900.470.166-4)").
7. Mantener actualizada la tabla de empresas con perfil en `docs/ARQUITECTURA.md`.
